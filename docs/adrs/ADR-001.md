# ADR-001: Decisões Arquiteturais

## Status

Aceito

## Contexto

O b3-selic-pre começou como um script CLI simples e evoluiu para um aplicativo desktop com múltiplas visualizações, análise textual e cache. As decisões abaixo foram tomadas ao longo do desenvolvimento para suportar essa evolução de forma sustentável.

## Decisões

### 1. Clean Architecture (4 camadas)

**Decisão:** Organizar o código em `domain/`, `application/`, `infrastructure/` e `presentation/` sob `src/b3_selic_pre/`.

**Motivação:** Separação clara entre regras de negócio (`domain/`), lógica de aplicação (`application/`), comunicação com mundo externo (`infrastructure/`) e interface com usuário (`presentation/`). Facilita testes e substituição de componentes (ex.: trocar Tkinter por outra GUI no futuro).

### 2. GUI como modo padrão

**Decisão:** Executar sem argumentos abre a interface gráfica (Tkinter). CLI é acionada via flags explícitas (`--today`, `--yearly`).

**Motivação:** O público-alvo (analistas) prefere interação visual. A CLI permanece disponível para scripts e automação.

### 3. Matplotlib para gráficos

**Decisão:** Usar matplotlib com backend TkAgg para renderização de gráficos.

**Motivação:** Biblioteca madura, suporta gráficos de linha, área, 3D e exportação de imagem. Integração direta com Tkinter via `FigureCanvasTkAgg`.

### 4. Dados da B3 via duas fontes

**Decisão:** Usar a API JSON paginada (`GetList`) para consultas pontuais e o CSV oficial (`GetDownloadFile`) para datas históricas.

**Motivação:** A API paginada é mais rápida para a data corrente. O CSV oficial serve como fonte de maior confiança para datas passadas e alimenta a visão consolidada anual.

### 5. Cache baseado no XDG Basedir Spec

**Decisão:** Armazenar cache em `~/.cache/b3-selic-pre/rates/` e configurações em `~/.config/b3-selic-pre/settings.json`.

**Motivação:** Conformidade com o padrão XDG (Linux) e organizações similares no Windows/macOS. Cache com TTL de 30 min para dados de hoje (voláteis) e retenção infinita para datas passadas.

### 6. Motor de análise baseado em regras

**Decisão:** Classificar a curva por regras configuráveis (thresholds de juro nominal, real, inclinação, prêmio) em vez de ML.

**Motivação:** Transparência total da lógica, baixa complexidade computacional, thresholds ajustáveis pelo usuário via `settings.json`.

### 7. PyInstaller para distribuição

**Decisão:** Empacotar como binário único via PyInstaller, build automatizado por GitHub Actions.

**Motivação:** Distribuição zero-dependência para o usuário final. CI/CD cross-platform (Linux, Windows, macOS) com releases automáticas.

### 8. OpenSpec / Spec-Driven Development

**Decisão:** Toda mudança deve ter proposal, design, tasks e spec atualizados antes de ser mergeada.

**Motivação:** Rastreabilidade das decisões, documentação viva do sistema, e revisão consistente antes da implementação.

## Consequências

- A estrutura de 4 camadas adiciona boilerplate para features simples, mas evita acoplamento e mantém testabilidade.
- O cache em disco resolve o problema de lentidão da API da B3, mas exige gerenciamento de expiração e corrupção.
- O motor baseado em regras é limitado a padrões pré-definidos; novas classificações exigem alteração de código (não aprendizado).
- O PyInstaller gera binários grandes (~50-80 MB) devido ao empacotamento do Python + dependências.

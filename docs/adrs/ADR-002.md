# ADR-002: Quality Gate como pré-requisito para Release

## Status

Proposto

## Contexto

O workflow de release (`release.yml`) atualmente constrói binários PyInstaller e publica a GitHub Release sem executar verificações de qualidade — lint, testes, cobertura, complexidade, duplicação de código ou análise de segurança. Isso cria o risco de distribuir código com qualidade degradada ao usuário final.

A RFC-002 define um quality gate abrangente com thresholds bloqueantes (cobertura >= 85%, mutation score >= 80%, complexidade ciclomática <= 10, duplicação <= 10%, zero vulnerabilidades HIGH no semgrep), mas esse gate não era invocado pelo pipeline de release.

## Decisão

**O workflow de release será gateado pelo CI.** O `release.yml` passará a incluir um job `ci` que chama `ci.yml` via `workflow_call`, e o job `build` dependerá de `ci` (`needs: ci`). Nenhum binário será construído ou publicado sem o quality gate passar integralmente.

```
release.yml (após mudança)
├── ci: workflow_call → .github/workflows/ci.yml
│   ├── lint (Python 3.12)
│   ├── test (Python 3.12 + 3.13)
│   └── quality-gate (Python 3.12 + 3.13)
│       ├── lint
│       ├── complexity (radon, xenon, lizard, complexity_metrics.py)
│       ├── duplication (jscpd)
│       ├── test + coverage (pytest-cov >= 85%)
│       ├── security (semgrep ERROR blocking)
│       └── mutation-check (score >= 80%)
├── build (needs: ci, matrix linux/windows/macos)
└── release (needs: build)
```

### Motivação

- **Segurança:** Código com vulnerabilidades ou baixa qualidade nunca chega ao usuário final
- **Confiança:** Cada release é garantidamente testada, com cobertura e mutation score conhecidos
- **DRY:** O `ci.yml` é reutilizado tanto em push/PR quanto em release, sem duplicação de lógica
- **Fail-fast:** Problemas de qualidade são detectados antes de gastar tempo de build (especialmente relevante para builds cross-platform que consomem ~15 min)

### Alternativas consideradas

1. **Duplicar os steps do CI dentro do release.yml** — Rejeitada por violar DRY e dificultar manutenção
2. **Composite action** — Rejeitada porque composite actions não suportam condicionais, secrets, ou cache entre jobs com a mesma flexibilidade que `workflow_call`
3. **Manter release sem gate** — Rejeitada porque é exatamente o problema que a RFC-002 resolve

## Consequências

- Releases que falharem o quality gate não produzirão binários. O desenvolvedor deve rodar `make quality-gate` localmente e corrigir problemas antes de criar a tag.
- O tempo total do pipeline de release aumenta (CI completo roda antes do build), mas o cache de `.venv` mitiga parte do overhead.
- O `mutation-check` depende de `mutants/mutmut-cicd-stats.json` pré-existente. O desenvolvedor é responsável por rodar `make mutation-run` localmente antes do push da tag.
- Em caso de falha no gate, o release pode ser re-disparado via `workflow_dispatch` após a correção.
